# Implementation Plan: Bulk Work History Edit Import

## Overview

Build bottom-up, in dependency order: the export's hidden id column first (everything else needs it to exist before it can be tested against), then the read-only preview path, then the commit path (which reuses `Approve`/`RejectWorkHistoryEditRequestAction` directly rather than adding new apply logic), then the frontend, then the full test suite, then final formatting/typecheck. Each backend phase ends with a checkpoint running the relevant test slice before moving on, since later phases depend on earlier ones behaving correctly (preview's row shape is resubmitted verbatim to commit).

### Implementation Strategy
- **Foundation-first for the export column**: nothing else can be built or tested until `Check_In_Id_Column` exists, since preview's row-matching depends on it end-to-end.
- **Reuse over new logic**: the commit action is thin orchestration around the existing `ApproveWorkHistoryEditRequestAction`/`RejectWorkHistoryEditRequestAction` — no task should reimplement apply/reject/drift-detection.
- **Risk-first on the overnight-rollover date heuristic** (design.md "Key Design Decisions"): implement and test this in isolation before wiring it into the full preview action, since it's the one piece of genuinely new logic with no existing precedent to copy.
- **Feature-slice for testing**: a lifecycle test (export → edit → preview → commit) is written early enough to catch integration issues before polishing edge cases.

## Notes

- **No new database tables or migrations.** This feature reuses `work_history_edit_requests`/`work_history_edit_request_items` as-is (design.md); the only schema-adjacent change is the additive export column, which is a generated file, not a table.
- **Ordering dependency**: Phase 2 cannot be meaningfully tested without Phase 1 (preview matches rows by the column Phase 1 adds), and Phase 3 reuses row shapes Phase 2 defines — do not reorder these phases.
- **Highest-risk item**: the overnight-rollover date-resolution heuristic (Phase 2, tasks 6 and 9.2) is new logic with no existing precedent in the codebase to copy from; it gets its own isolated unit tests (task 6.2) before being wired into the full reconciliation flow, so a mistake there is caught early and cheaply.
- **Deliberately avoided**: re-parsing the uploaded file at commit time. Commit re-validates using the same `old_value`-vs-live-data check `ApproveWorkHistoryEditRequestAction` already performs, which is both simpler and exactly matches how the single-record flow already detects staleness (`WORK_HISTORY_EDIT_REQUEST_DATA_CHANGED`).
- **Do not skip the `Check_In` row lock in task 12.2.** Without it, two concurrent commits (or a commit racing a single-record submission) could both pass the "no pending request yet" check and both insert one, since `(check_in_id, status)` has no unique DB constraint — only an index. This mirrors `CreateWorkHistoryEditRequestAction`'s existing guard; per this repo's Test Design Rules, this is prevented by the lock, not by a multi-threaded test.
- Per this repo's CLAUDE.md, translation keys must be added via `t(...)` first, then run through `pnpm trans:prepare` / fill `vi`+`ja` / `pnpm trans:apply` (Phase 4, task 20) — never hand-edit the locale JSON files.
- Task Completion Checks (`pnpm lint:fix`, `pnpm prettier`, `pnpm typecheck` for frontend; `npm run prettier`, `npm run pint` for backend) are run once per phase's checkpoint informally, and formally as the final Phase 6 task.
